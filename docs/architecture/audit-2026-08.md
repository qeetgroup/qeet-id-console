# Qeet ID Console — Architecture Audit (2026-08)

Evidence-based, read-only audit. Findings tagged **Verified** / **Likely** /
**Needs-investigation**. Baseline: 192 tests, boundaries CI-enforced, all gates green.

## A. Executive summary

Strong, enterprise-grade codebase (~8.5/10). Layered architecture
(`modules / platform / shared / routes`) is real and CI-enforced: **zero**
shared→domain, platform→domain, or module→module-internal violations; **zero**
hand-written `any`; no `console`/`alert`/`dangerouslySetInnerHTML` leaks. The
security core holds up (no authorization bypass; tools run under the operator
token; secrets in-memory-only; redaction real and used).

The real risks are **adoption gaps, not design flaws** — good primitives not
wired in everywhere `SECURITY.md` claims. Top items: 50+ inline `error.message`
renders bypass `userMessageForCode`; step-up wired at 1 of ~10 sensitive sites
(signing-key rotation has none); 2 Qeet AI tools mutate without confirmation
(`enable_user`, `update_user`). Structural debt: 52/99 routes do data access
directly. 9 modules have zero tests (incl. authentication/authorization/users/security).

## F. Security findings

- **P1-1** 50+ inline `error.message` renders bypass `userMessageForCode`.
- **P1-2** `useSensitiveAction` adopted at 1 site; signing-key rotation + secret
  rotate/delete + sessions + GDPR use plain confirms (dead-end on `step_up_required` — Likely).
- **P1-3** Qeet AI `enable_user` (restores sign-in) + `update_user` mutate without confirmation.
- **P2** ✅ persisted `message.content` + derived title now PII-masked (`sanitizeForPersistence`);
  ✅ markdown `href` scheme allowlist (http(s)/mailto/same-origin only — blocks `javascript:`/`data:`);
  ✅ `X-Request-Id` now on SSE + refresh fetches; ✅ secret rotation moved off native `window.prompt`
  to a masked-input Sheet (routed through the step-up pipeline). **Remaining:** redaction is
  email/IPv4 only (not names).
- **Needs-investigation** backend must reject tampered `userId`/`tenantId` in effective-permissions path.
- **Accepted/deferred** tokens in localStorage (ADR-0002); client-side guards.
- **Verified-good** no privilege bypass; enabledTools double-gate; step-up in AI path;
  secrets in-memory-only; redaction denylist real+used; authz fails closed.

## I. Target architecture

Freeze the structure. Refinement-in-place: thin routes (data access → module hooks);
`shared/utils/format.ts` + reuse `data-export`; a `sessions` contract (type + table);
exported query-key factories; step-up + safe-error adoption at all sensitive sites.

## J. Roadmap

- **P0** enable_user/update_user confirm; step-up at signing-key rotate + secret rotate/delete;
  route auth/secret inline error renders through `userMessageForCode`.
- **P1** consolidate duplication (A1/A2/A3/B1/B3/B4/C2); thin the fattest routes.
- **P2** ✅ markdown href allowlist; ✅ X-Request-Id on SSE/refresh; ✅ mask persisted content/title;
  ✅ replace `window.prompt` secret entry (masked Sheet); ✅ i18n missing-key handler
  (humanized fallback + dev warning — no raw dotted keys reach the UI). **Remaining:**
  broaden tests for auth/authz/users + qeetai confirm gates; mask personal names.
- **P3** lazy-load heavy deps; axe smoke tests; CODEOWNERS/PR template.

## K. First module: authentication

Highest-severity verified findings (signing-key rotation = tenant-wide token-forgery
blast radius, no step-up — now on the step-up pipeline; secret entry via `window.prompt` —
now a masked Sheet; error leaks; zero tests) and it is the product's core security domain.
The Qeet AI `enable_user`/`update_user` confirm gate is a small P0 to fix alongside.
Remaining deep-clean for this module: unit tests (still zero).
